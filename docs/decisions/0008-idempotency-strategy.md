# 0008 - Idempotency strategy

## Decision
Layered idempotency: prefer a client-supplied idempotency key (the walking-skeleton's own
intake form generates one); fall back to a server-derived key — a hash of normalized email
+ message + a 5-minute time bucket — when no client key is present. Enforce uniqueness via
a database `UNIQUE` constraint with `INSERT ... ON CONFLICT DO NOTHING`, and respond to a
detected duplicate with `200 OK` and `duplicate: true`, never an error status.

## Context
"Duplicate" hides three distinct scenarios that need different handling:
1. The same event delivered twice (network retry, double-click, webhook redelivery after
   a crash before responding) — the textbook idempotency problem.
2. A person resubmitting minutes later, unsure the first attempt worked — not a technical
   retry, but should still collapse into one lead so the team isn't notified twice for one
   visit.
3. A person submitting a genuinely new, separate inquiry later — must NOT be deduped.

No single mechanism distinguishes all three perfectly; the design is intentionally
layered and best-effort rather than claiming false precision.

## Options Considered
- **Client-supplied key only**: exact protection for scenario 1, but only if we control
  the form; a real third-party client form (Phase 11 concern) likely can't supply one.
- **Server-derived key only** (hash of contact info + time window): works regardless of
  form control, but is inherently a heuristic — window size and hash inputs trade off
  false positives (suppressing a real second inquiry) against false negatives (letting an
  accidental resubmit through as a second lead).
- **Layered: client key when available, server-derived fallback otherwise** (chosen):
  gets exact protection where we control both ends, graceful degradation where we don't.

For the server-derived key's hash inputs:
- **Email + time bucket only**: coarser — any submission from the same contact within the
  window counts as one event regardless of message content.
- **Email + message + time bucket** (chosen): finer-grained — only an exact-content repeat
  within the window dedupes; two different messages sent close together are treated as two
  distinct leads, since they represent different inquiries even if sent minutes apart.

For the time bucket width: 5 minutes (chosen) balances covering realistic double-
click/retry/resubmit timing against the risk of a wider window collapsing two genuinely
separate same-day inquiries.

For the duplicate response: **200 OK + `duplicate: true`** (chosen) over 409 Conflict,
because from the caller's perspective (the form, or a retrying HTTP client) a retried
idempotent request is a success — surfacing it as an error risks a legitimate frontend
showing a false failure to the person who submitted the form.

## Decision Made
- Primary key source: client-supplied `Idempotency-Key`, generated by the intake form on
  load (a hidden UUID field), since we control the walking skeleton's own form.
- Fallback key source (used only when no client key is supplied): `hash(normalize(email) +
  normalize(message) + floor(received_at / 5min))`.
- `idempotency_source` column records which path produced the key for a given row.
- Enforcement: a database `UNIQUE` constraint on `idempotency_key`, with
  `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING`, then read back whichever row
  exists (new or pre-existing) and respond identically either way. A check-then-insert at
  the application level is explicitly rejected — it has a race condition when two
  identical requests arrive concurrently, since both could pass the check before either
  inserts.
- On a detected duplicate, the intake endpoint returns `200 OK` with `duplicate: true` and
  the existing lead's current per-step status. It does **not** attempt to resume any
  `pending`/`failed` downstream steps synchronously — that is deliberately deferred to a
  separate reconciliation mechanism in Phase 4, keeping the intake endpoint
  single-purpose: accept and dedupe, nothing else.

## Why
This gets the strongest available protection (client key) where we control both ends,
while degrading gracefully to a reasonable heuristic where we don't — which is also the
more realistic design for Phase 11, where a real client's form may not supply a key at
all. Enforcing uniqueness at the database layer, not the application layer, closes the
race-condition gap that a naive check-then-insert leaves open, and is the direct payoff of
choosing Postgres from day one ([[0003-database]]).

## Trade-offs
- The email+message+time-bucket fallback can still be fooled: a person resubmitting the
  *same* message content just outside the 5-minute window is treated as a new lead
  (accepted false negative — favors not losing a real inquiry over perfect dedup). A
  person submitting two genuinely different but coincidentally near-identical messages
  within the window would incorrectly dedupe (accepted false positive — judged rarer and
  lower-cost than the alternative).
- Requires the walking skeleton's intake form to generate and send an `Idempotency-Key`;
  any client integration that doesn't (a real third-party form) relies entirely on the
  fallback's heuristics, which are weaker than an exact client-supplied key.
- Resuming a stuck (`pending`/`failed`) row on duplicate detection is intentionally not
  handled here — see Phase 4 (Reliability Hardening) for the reconciliation mechanism that
  will cover it.
