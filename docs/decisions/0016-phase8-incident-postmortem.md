# 0016 - Postmortem: Phase 8 secret exposure incident

## Summary
During the first live Render deployment, a copy-paste error corrupted an environment
variable, which led to two real secrets (the Resend API key and the production
`WEBHOOK_SIGNING_SECRET`) being written in plaintext into Render's log stream, and from
there into a screenshot shared for diagnosis and into this project's own chat history.
Both credentials were rotated (twice, on request, out of extra caution), two real code
bugs were found and fixed as a direct result, and a full public-release audit confirmed
no secret exists anywhere in the repository or its history. This is a real incident that
happened during this project's own deployment, not a hypothetical chaos-pass scenario —
recorded here as one, per Phase 9's purpose.

## Timeline
1. App deployed to Render; `/health` passing.
2. First live signed lead: HubSpot and Slack succeeded; the Resend (acknowledgement
   email) step silently never completed — `ack_status` stuck at `pending`,
   `ack_attempts=0`, no error recorded at all.
3. The background reconciliation sweep ran on schedule but made no visible progress on
   that row — same silent, unrecorded outcome every time.
4. Diagnosis required reading Render's raw log output directly (no automated alert had
   fired — itself a finding, see below). The traceback revealed `httpx.LocalProtocolError:
   Illegal header value`, containing the literal (corrupted) value of `RESEND_API_KEY`.
5. That corrupted value contained the Resend key immediately followed by a newline and
   `WEBHOOK_SIGNING_SECRET=<value>` — meaning a dashboard paste had absorbed two lines
   into one field. Both the Resend key and the production signing secret were now in
   plaintext in Render's persisted logs, and, once shared for diagnosis, in a screenshot
   and in this conversation's own history.
6. Both credentials were rotated immediately. The first rotation attempt of the signing
   secret still failed live verification — traced to an invisible trailing newline in
   Render's text field, the same underlying failure mode as the original incident, just
   smaller in consequence.
7. Root cause fixed in code (not just re-rotated around): `app/config.py` now strips and
   validates every secret-bearing setting at startup.
8. A second, independent bug was found while diagnosing the first: an adapter's
   unexpected exception was being silently logged and dropped by `app/pipeline.py`, with
   no Sentry alert and no attempt recorded — fixed to classify as transient, record the
   attempt, and alert immediately.
9. Both fixes deployed; end-to-end verification (a real signed request against the live
   URL) confirmed all three integrations succeeding.
10. At the user's request, both credentials were rotated a **second** time under a
    stricter protocol: self-generated secrets written directly to a file and never
    printed; the provider-issued key rotated entirely within the user's own dashboard,
    never typed to the assistant.
11. A full public-release audit followed (working tree, all tracked files, complete git
    history, the live GitHub repo verified independently via its API, `.gitignore`
    practically tested, README guidance reviewed) — clean.

## Root causes
- **Human/UX**: Render's environment-variable text fields don't visually surface
  trailing whitespace or newlines, making a multi-line copy-paste silently corrupt a
  single-line value. This happened independently twice, across two different rotations.
- **Missing input validation**: no code path checked a secret-bearing setting for
  whitespace corruption at startup, so a bad value wasn't caught until it caused a
  downstream, harder-to-diagnose failure.
- **Exception messages can contain sensitive data**: `httpx`'s own protective error
  (correctly refusing to send an illegal header) included the illegal value verbatim in
  its message, and this project's own logging faithfully recorded that full message —
  meaning any exception whose text happens to embed a secret will leak it into logs by
  default, unless something upstream prevents the corrupted value from ever reaching that
  call in the first place.
- **A second, unrelated bug compounded diagnosis time**: unexpected exceptions inside an
  adapter call were silently dropped rather than alerted or recorded, so there was no
  automated signal that anything was wrong at all — a human had to notice the missing
  acknowledgement email and go looking.

## What changed as a result
- Both credentials rotated (twice).
- `app/config.py`: whitespace stripped and validated on every secret-bearing setting.
- `app/pipeline.py`: unexpected adapter exceptions now classified transient, recorded,
  and reported to Sentry immediately, instead of silently dropped.
- Working protocol established for any future credential handoff: a secret generated by
  the assistant is written directly to a file and never printed to chat or tool output; a
  secret issued by an external provider is rotated entirely within that provider's own
  dashboard and never typed into the conversation at all.
- Full audit performed and documented (ADR 0013 covered the pre-publish audit; this
  incident prompted a second, independent full audit afterward, which also passed clean).

## What this confirms about the system's actual design
Despite the incident, several of this project's earlier design decisions did exactly
what they were built for: HubSpot and Slack succeeded and were completely unaffected by
the Resend-specific failure (ADR 0009's independence guarantee, working as intended,
under a real fault rather than a simulated one). The lead itself was never lost — it sat
safely in the database the entire time, retriable, exactly per ADR 0007/0008's design.
The gap was specifically in *visibility* (no alert fired) and in *input hygiene* (no
validation caught the corrupted value) — both now closed.

## Trade-offs / follow-ups not taken
- No general-purpose secret-scanning pre-commit hook was added. The audits performed
  were thorough and manual/scripted per-incident; a standing automated scanner (e.g. a
  pre-commit hook checking new content against known secret shapes) would catch future
  incidents earlier but wasn't judged necessary given how rigorously this project already
  checks before every commit and push.
- Render's own environment-variable UI wasn't changed (outside this project's control);
  the mitigation is entirely on this project's side (validation) rather than assuming the
  hosting platform's UI will prevent the mistake.
